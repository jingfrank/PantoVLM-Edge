### 📌 项目名称：动车组受电弓网多模态实时视觉故障监测系统 (VLM Edge-Cloud)
* **担任角色**：多模态算法与高性能系统部署负责人
* **核心技术栈**：Qwen3-VL-4B、vLLM、PagedAttention、Continuous Batching、Docker、NVIDIA Jetson AGX Orin、OpenCV、RTSP 流媒体、UDP 二进制报文、PHM 故障上报

#### 🌟 核心职责与量化成果 (STAR 原则)：
1. **算法架构创新（动静分离两阶段流水线）**：针对传统闭集目标检测对未知外来悬挂物泛化差的痛点，引入 Qwen3-VL 视觉语言大模型。设计 Stage 1（4 帧 640P 时序轻量分类）与 Stage 2（单帧 960P 高清原图 `<point>` 空间定位）级联架构，实现对微小羽毛、薄膜等未知杂物的零样本开集检出，定位误差 < 1.4%。
2. **抗虚警核心算法（跨窗口时序一致性追踪器）**：针对大模型单帧静态幻觉导致的误报警，自研 `TemporalConsistencyTracker` 空间-时序状态机（引入 SUSPECT 疑似观察期与 CONFIRMED 连续命中确认机制）。通过将物理时钟解耦为窗口步长（Window Gap TTL），**消除 GPU 算力抖动带来的时钟漂移，成功过滤 95% 以上的单帧随机虚警**。
3. **高性能推理加速（vLLM 微服务 + 推测并发执行）**：利用 Docker 容器化部署 vLLM 生产级微服务，结合 PagedAttention 显存零碎片管理与连续批处理技术；设计推测多线程并发执行架构（Speculative Concurrency），**将滑动窗口端到端诊断耗时从 5,500 ms 极限压缩至 1,068 ms（提速近 4 倍，吞吐量提升 300%）**。
4. **车载全流程工业级闭环**：打通多路 RTSP 异步采样管线、进程安全看门狗、0xFF 0x20 标准二进制 UDP 告警报文封装、PHM 设备健康状态上报与 OSD 双侧水印事件截图自动落盘，完成系统工程化闭环。

## 二、 面试深度技术问答与杀手锏话术库 (Top 8 Q&A)

### Q1：为什么要在工业检测中用多模态大模型（VLM），而不是传统的 YOLO 或 Faster-RCNN？
* **回答要点**：
  1. **闭集 vs 开集**：受电弓上的火花、结构断裂是闭集目标，YOLO 可以搞定；但“悬挂异物”本质上是**开放词表（Open-Vocabulary）开集问题**，现实中可能遇到羽毛、彩色塑料袋、风筝线、死鸟、棉纱等成百上千种形态，传统检测器无法对未知目标进行特征激活。
  2. **多模态语义先验**：Qwen-VL 在海量图文对中预训练过，天生理解什么是“外来附着杂物”，通过精细化 Prompt 约束，能以零样本（Zero-shot）方式直接定位未知杂物的中心坐标 `<point>`。

---

### Q2：大模型推理那么慢，怎么满足高铁车载监控的实时性？
* **回答要点**：
  1. **采样与时序窗口分级**：工业上不需要每秒跑 25 次大模型，我们采用 **1 FPS 抽样 + 4 帧滑动窗口**，诊断周期为 4 秒。
  2. **动静分离降 Token**：Stage 1 动态时序分类将 4 帧等比缩放至 640P（Token 量降低 75%）；Stage 2 仅取单张原图高清帧进行点定位。
  3. **vLLM 推理优化**：引入 vLLM PagedAttention、CUDA Graph 拓扑捕获与推测多线程并发，将端到端耗时由 **5.5 秒压至 1.06 秒**，不仅完全不积压，还为系统留出了 3 倍的算力裕量。

---

### Q3：大模型经常出现“单帧幻觉（Hallucination）”，你们在工业现场如何保证不乱报假警？
* **回答要点**：
  1. **强负样本 Prompt 排除**：在 Prompt 中明确定义受电弓本体所有机械结构（左右弧形弓角、金属包边、绝缘套管、接触网吊弦线）绝不是异物，消除固有结构偏见。
  2. **自研 `TemporalConsistencyTracker`**：
     * 真实物理异物在碳滑板上的几何空间坐标在相邻时间窗口是稳定连续的（$\Delta d < 100\text{px}$）；
     * 大模型单帧幻觉具有“瞬时性”和“空间跳跃性”；
     * 只有在第 1 个窗口标记为 `SUSPECT`，并在第 2 个窗口相同位置再次命中，才晋升为 `CONFIRMED`。单帧误报直接在下个周期淘汰，整段 10 分钟视频虚警归零。

---

### Q4：你们在时序滤波中遇到了什么 Bug，又是怎么解决的？
* **回答要点**：
  * **背景问题**：早期我们在追踪器中设定了物理墙上时钟 `TTL = 6.0s`。在本地单图测试时完美，但在端到端视频流中，由于 GPU 负载导致窗口耗时略有波动（如两个窗口之间由于排队耗时达到了 7 秒），导致第 2 个窗口到达时，上一个候选已经被 6.0s 超时删除了，造成真实异物永远无法累计到 2 次命中。
  * **解决之道**：我们将依赖物理时钟的机制重构为**基于窗口序号步长（Window Gap TTL）**的数学约束（`gap = current_window_id - last_window_id <= 2`）。这样无论底层 GPU 推理花 1 秒还是 10 秒，时序追踪逻辑在数学上具备严格的时间不变性。

---

### Q5：为什么选择用 vLLM 替代 HuggingFace 原生 Transformers？底层原理是什么？
* **回答要点**：
  1. **PagedAttention 显存虚拟化**：避免传统 Attention 连续显存预分配造成的显存碎片和 OOM，将 KV Cache 显存利用率从 20%~40% 提升至 90% 以上。
  2. **Continuous Batching（连续批处理）**：原生 Transformers 必须等待整个 Batch 全部生成结束才释放，而 vLLM 可以在 Token 级别迭代加入和移出请求。
  3. **预编译与 CUDAGraph**：消除了 PyTorch 算子动态调度的 CPU 开销。

---

### Q6：介绍一下你们的“推测多线程并发架构（Speculative Concurrency）”？
* **回答要点**：
  * **业务现状**：工业现场 99% 的画面都是正常清晰的（`spk=0, dirt=0`）。
  * **传统串行**：必须等 S1 跑完（1.0s），再决定跑 S2（1.0s），总耗时 2.0s。
  * **推测并发**：主程序通过 `ThreadPoolExecutor` 同时将 S1（4帧视频）和 S2（单图定位）发给 vLLM。
  * **网关仲裁**：双路结果返回后，主线程充当门控仲裁器（Gate Arbiter）——若 S1 突发脏污/大火花，则直接丢弃 S2 结果；若 S1 正常，则直接采纳 S2。
  * **收益**：总耗时由 $T = S1 + S2$ 变为 $T = \max(S1, S2) \approx 1.06\text{s}$，几乎不增加额外硬件开销便让响应速度翻倍。

---

### Q7：在 NVIDIA Jetson AGX Orin 边缘端部署时，遇到了什么底层驱动问题？
* **回答要点**：
  * **问题**：边缘端工控机使用的是 JetPack 5.1.4（L4T r35.x 内核），其内核驱动 `nvgpu.ko` 与 `libcuda.so` 强绑定在 CUDA 11.4。而现代 vLLM (v0.6+) 底层算子强制依赖 CUDA 12.1+。
  * **技术决策**：在工业现场已稳定运行其他关键传感器驱动的前提下，避免高风险的刷机操作；我们设计了 **C/S 微服务架构**，在车载工控机部署轻量级 Python 客户端，将高并发推理任务解耦至专用 GPU 容器中，既保证了系统稳定性，又为未来升级 JetPack 6.0 (CUDA 12.6) 预留了无缝切换路径。

### Q8：如果视频流中出现大量 OpenCV/FFmpeg 报错并导致 `malloc(): unsorted double linked list corrupted` 崩溃，怎么定位和解决？
* **回答要点**：
  * **根本原因**：在频繁重连视频流的异常处理中，主线程调用了 `cap.release()` 释放底层 C++ 资源，而背景拉流子线程仍处于 `cap.read()` 阻塞中，导致 C 底层堆指针发生双重释放（Double Free）与竞态损坏。
  * **解决之道**：重构 `RTSPStreamSampler.stop()`，先发送退出标志并调用 `thread.join(timeout=1.5)` 确保子线程完全退出后，再在主线程安全调用 `cap.release()`，彻底消除内存溢出崩溃。
